01 · The one-minute version

Git ≠ GitHub

Git is a tool. GitHub is a website built around that tool. You could use Git for years and never touch GitHub — but as a team developer, you'll use them together every day.

GITVersion control system

  • What it is: software that records every change to your code, forever.
  • Why: so you can go back, compare, and never lose work.
  • Runs mainly on your computer — no internet needed.
  • Keeps a full, searchable version history.
  • Lets you branch — try things safely on the side.
  • Lets you merge — bring finished work back together.

GITHUBOnline hosting & collaboration platform

  • What it is: a website that stores Git repositories in the cloud.
  • Gives every repo a remote home your whole team can reach.
  • Adds Pull Requests — propose changes, don't just push them.
  • Adds Code Review — teammates read and discuss your diff.
  • Adds Issues & Projects — plan and track work.
  • Where most open-source collaboration happens.

02 · The master map

Everything Git does falls into four jobs

Before you reach for a command, work out which of these four jobs you're actually trying to do. That's usually enough to know which command you need.

A · Setup & starting

Get a repo to work in

git configgit initgit clone

init starts Git tracking in a brand-new folder where no repo exists yet. clone copies a repo that already exists on GitHub down to your machine. You almost never use both on the same project.

B · Checking & tracking

See what's changed

git statusgit diffgit loggit show

Your "look before you act" commands. status for what's changed, diff for exact line changes, log for history.

C · Saving changes

Turn edits into a checkpoint

git addgit commit

The most-used pair in Git. add prepares changes, commit saves them permanently to local history. See the full diagram below.

D · Connecting to GitHub

Sync with the remote

git remoteremote add origingit pushgit pullgit fetch

Bridges your local repo and GitHub. push sends commits up, pull/fetch bring them down.

08 · What's inside GitHub

GitHub, broken into five core tools

  • GITHUB
    • Repository — where your project's code + full history lives online
    • Pull Request — propose merging your branch, with a reviewable diff
      • Code Review — comments, approvals, requested changes
    • Issues — tracked bugs, tasks, and feature requests
    • Projects — a Kanban board to plan work across a sprint
    • README — the front page: what it does, how to run it
09 · What not to upload

.gitignore — the do-not-track list

A plain text file that tells Git which files to never stage, commit, or upload — even if they're sitting right there in your project folder.

Project/
├── src/ ✔ tracked ├── README.md ✔ tracked ├── .env ✕ ignored ├── node_modules/ ✕ ignored ├── target/ (build output) ✕ ignored └── application-secrets.properties ⛔ never commit
Already committed a secret? Removing it in a new commit isn't enough — it still exists in history. Rotate/revoke the key immediately, then clean history carefully (or ask a senior teammate for help).
10 · I made a mistake

What should I do?

  • I made a mistake
    • Changed a file, haven't staged it → git restore <file>
    • Staged it, haven't committed → git restore --staged <file>
    • Already committed → git revert <commit>
    • Need to shelve it temporarily → git stash
    • Need to inspect history first → git log
Advanced / destructivegit reset --hard permanently discards changes — it's not a beginner default. Only use it once you fully understand what it deletes, ideally after a git stash.
11 · When two people edit the same line

Merge conflicts, demystified

Developer A edits line 12
+
Developer B edits line 12
→

→
CONFLICT ⚠
→
Manually choose the right code
→

What it is
Git can't automatically decide which change should win, so it stops and asks you.
How to spot it
Git marks the file with conflict markers.
<<<<<<< HEAD
your version
=======
their version
>>>>>>> feature-branch
How to resolve it
Open the file, decide (or combine) the correct version, delete the markers, then stage and commit.
Prevent it
Talk to your teammate before both of you touch the same file — most conflicts are a communication gap, not a Git problem.
